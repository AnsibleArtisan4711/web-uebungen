# 20.5 Dokumentationsstandards und Wartungsplan

> Modul 20 · Lehrplan 20.6 · Geschätzter Zeitaufwand: 75 Minuten

## Lernziele

- Du schreibst eine README, die Fremden den Einstieg erlaubt.
- Du hältst eine Entscheidung als ADR fest (Kontext, Entscheidung, Alternativen, Konsequenzen).
- Du legst ein Betriebshandbuch an, ohne Geheimnisse ins Repository zu schreiben.
- Du prüfst Dokumentation automatisch auf Vollständigkeit und tote Verweise und kennst die Grenzen.

## Voraussetzungen

20.1 bis 20.4; 19.6 (Wartungsplan)

## Ausgangslage

Das Portfolio hat Werkzeuge und Prüfungen, aber wer neu dazukommt, findet nur eine README aus Modul 19. Jetzt entstehen: eine vollständige [README](../portfolio/modul-20/README.md), Entscheidungsprotokolle in [`docs/adr/`](../portfolio/modul-20/docs/adr/), ein [Betriebshandbuch](../portfolio/modul-20/docs/betriebshandbuch.md) als Vorlage, der [Wartungsplan](../portfolio/modul-20/docs/wartungsplan.md) aus Modul 19 und das Skript [`doku-check.js`](../portfolio/modul-20/tools/doku-check.js).

## Aufgabe

1. Beantworte (Lehrplan-Aufgabe 5): Welche Inhalte gehören in eine README? Führe `npm run doku` auf dem README-Stand von Modul 19 aus und vergleiche mit deiner Liste.
2. Schreibe die README so, dass der Check bestanden wird, ohne Abschnitte nur für den Check anzulegen. Wo gehören Ansprechpersonen hin, wenn das Repository öffentlich ist?
3. Schreibe einen ADR mit der Vorlage `docs/adr/vorlage.md` für eine Entscheidung dieses Kurses (z. B. warum das Stylesheet aus Quelldateien gebaut wird). Lies danach die drei vorhandenen ADRs: Welche Aussagen darin sind belegt, welche Annahmen?
4. Fülle das Betriebshandbuch für dein Projekt aus. Welche Angaben schreibst du **nicht** hinein?
5. Prüfe den Check: Entferne einen Abschnitt aus einem ADR und füge einen Verweis auf eine nicht vorhandene Datei ein. Wird beides gefunden?
6. Ergänze den Wartungsplan um die QS-Punkte dieses Moduls (Validierung, Browser-Tests, Dokumentation) mit Intervall und Zuständigen.

## Hinweise

- Eine gute README beantwortet in dieser Reihenfolge: Was ist das? Wie starte ich es? Wie prüfe ich meine Änderung? Wen frage ich?
- ADRs werden nicht überschrieben: Ändert sich eine Entscheidung, bekommt sie einen neuen ADR, der den alten ablöst (Status).
- Der Check prüft das Vorhandensein, nicht die Richtigkeit. Dafür bleibt das Review.

## Lösung

1. README: Zweck, Voraussetzungen, Installation, Befehle (Entwicklung, Build, Test), Struktur des Projekts, Veröffentlichung, Konventionen (Verweis auf `CONTRIBUTING.md`), Ansprechpersonen. Gemessen: Mit der README aus Modul 19 (sie hatte Ansehen, Erste Schritte, Befehle, Hinweise) meldet `npm run doku` **5 fehlende Abschnitte** (Voraussetzungen, Struktur, Veröffentlichung, Konventionen, Ansprechpersonen) und einen Verweis im Betriebshandbuch auf eine zu dem Zeitpunkt noch nicht kopierte Datei (`release-checkliste.md`). Beim Vergleich mit deiner Liste: Der Check ist an die Lehrplan-Aufzählung angelehnt, nicht allgemein gültig.
2. Die README dieses Moduls ([`README.md`](../portfolio/modul-20/README.md)) enthält alle acht Teile. Nach dem Schreiben: `npm run doku` → **0 Probleme** (3 ADRs, 9 Verweise geprüft). Ansprechpersonen: Platzhalter mit Rollen, keine Namen, E-Mail-Adressen oder Telefonnummern, solange das Repository öffentlich ist (Datenschutz, 18.6); im Betriebshandbuch steht, **wo** die Zugangsdaten liegen, nicht welche.
3. Die drei ADRs halten fest: (0001) statische Seite ohne Framework und CMS, (0002) CSP per Header und `<meta>`, (0003) Build nach `dist/` mit Hash-Dateinamen. Belegt sind darin gemessene Zahlen (Dateigrößen, Zeiten von PostCSS und Lightning CSS, Header-Einschränkung bei GitHub Pages laut Community-Diskussion), **Annahmen** sind die Randbedingungen (eine pflegende Person, seltene Änderungen) und die Einstufung „angenommen (Kursannahme)“. Wichtig ist, dass auch die Alternativen und die nicht ausprobierten Wege (Static-Site-Generator, Vite) mit dem Vermerk „nicht ausprobiert“ stehen.
4. Nicht ins Betriebshandbuch (und nicht ins Repository): Passwörter, Zugangsschlüssel (Tokens, `.pem`), private Telefonnummern und Wohnadressen, Backup-Passphrasen, Kontodaten. Stattdessen: Rolle, Ort der Ablage („Passwortmanager“), Ablaufdaten, Wiederherstellungsübung.
5. Gemessen in einer Kopie: Wird in einem ADR die Überschrift „Alternativen“ gelöscht und ein Markdown-Verweis auf die Datei `gibt-es-nicht.md` eingefügt, meldet der Check beides:
   `PROBLEM  docs/adr/0003-….md: Abschnitt „alternativen“ fehlt` und `PROBLEM  docs/adr/0003-….md: Verweis auf fehlende Datei „gibt-es-nicht.md“`, Rückgabewert 1. Der Check findet **nicht**, ob ein Abschnitt Unsinn enthält, ob ein Befehl in der README stimmt oder ob ein Betriebshandbuch aktuell ist.
6. Beispiel (zusätzlich zu den Zeilen aus 19.6):

   | Aufgabe | Intervall | Zuständig |
   |---|---|---|
   | Validierung und Linting über das ganze Projekt (`validate:html`, `validate:w3c`, `lint`) | bei jedem Release | Technik |
   | Browser-Tests, bei gewollten Änderungen Baseline erneuern (`e2e`) | bei jedem Release | Technik |
   | README, ADRs, Betriebshandbuch auf Aktualität lesen (`npm run doku` plus Lesen) | halbjährlich | Redaktion Technik |
   | Wiederherstellungsübung aus dem Backup | vierteljährlich | Technik |

   **Nicht getestet:** Barrierefreiheitserklärung als eigenes Dokument (der Lehrplan nennt sie; sie ist rechtlich geprägt und gehört nicht in einen Kurs ohne Rechtsberatung), automatisches Erzeugen von API-Dokumentation, Veröffentlichung der Dokumentation als Webseite.
