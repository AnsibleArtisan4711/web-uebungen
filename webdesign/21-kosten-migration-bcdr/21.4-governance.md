# 21.4 Governance und Wartungsregeln

> Modul 21 · Lehrplan 21.5 · Geschätzter Zeitaufwand: 75 Minuten

## Lernziele

- Du legst Zuständigkeiten fest (RACI) und erkennst, wo ein „A“ fehlt oder doppelt vergeben ist.
- Du beschreibst einen Änderungsprozess und einen Ablauf zum Auslaufenlassen veralteter Teile.
- Du formulierst Entwicklungsregeln so, dass eine Maschine sie prüfen kann.
- Du gehst mit Verstößen und Ausnahmen um, ohne die Regel aufzuweichen.

## Voraussetzungen

21.3; Modul 17 (Architektur) und 20 (Review, Namenskonventionen)

## Ausgangslage

Das Portfolio hat Regeln (Tokens, Ebenen, Namen). Ohne Prüfung zerfallen sie unbemerkt. In [`governance.md`](../portfolio/modul-21/docs/governance.md) stehen Zuständigkeiten, Prozess und Regeln. Fünf Regeln sind in [`tests/governance.test.js`](../portfolio/modul-21/tests/governance.test.js) als Tests umgesetzt und laufen mit `npm test`.

## Aufgabe

1. **Lehrplan-Aufgabe 6:** Formuliere Governance-Regeln für ein Frontend-Projekt (Zuständigkeiten, Änderungen, Browser-Support, veraltete Teile).
2. Erstelle eine RACI-Tabelle für fünf Aufgaben deines Projekts. Prüfe: Hat jede Zeile **genau ein** A?
3. Miss den Ist-Zustand für zwei Regeln **bevor** du sie als Test festschreibst (z. B. mit `grep` nach Farbwerten außerhalb der Tokens). Schreibe danach den Test.
4. Lasse `npm test` laufen. Eine Regel schlägt fehl. Entscheide, ob du den Code änderst oder eine begründete Ausnahme einträgst, und halte die Entscheidung fest.
5. Beschreibe den Ablauf, eine Komponente auslaufen zu lassen (Deprecation), und nenne die Rolle des Befehls `npm run namen`.

## Hinweise

- Eine Regel ohne Prüfung ist eine Bitte. Prüfe nur, was eine Maschine eindeutig entscheiden kann; der Rest bleibt Review.
- Vorsicht bei Mustersuche in Kommentaren: Der Test entfernt Kommentare vor der Suche, behält aber die Zeilennummern.
- Eine Ausnahme braucht Ort, Grund und Datum.

## Lösung

1. Beispielregeln: **Zuständigkeit** (jede Aufgabe genau eine verantwortliche Rolle), **Änderungen** (Ticket → Entscheidung → Pull Request mit Review → automatische Prüfung → Release → CHANGELOG), **Browser** (Policy mit Stufen A/B/C, siehe [21.5](21.5-css-sicherheit-third-party-und-browser-kompatibilitaet.md)), **Deprecation** (markieren, Ersatz nennen, Übergangszeit, Nutzung messen, entfernen). Ausgeschrieben in [`governance.md`](../portfolio/modul-21/docs/governance.md).
2. RACI-Beispiel in `governance.md` (Rollen Entwicklung, Gestaltung, Inhalt, Betrieb; sechs Aufgaben). Bei einer Einzelperson sind alle Rollen dieselbe Person; die Tabelle zeigt dann nur, welche Aufgaben welchen Hut brauchen. Der Bus-Faktor ist hier 1.
3. Gemessen **vor** dem Schreiben der Tests: Farbwerte (`#hex`, `rgb`, `hsl`) in `css/src/` außerhalb von `02-tokens.css`: **0** (in den Tokens: 25 Zeilen). `z-index` ohne Token: **0** (3 Verwendungen, alle `var(--z-…)`). `!important` in 2 Dateien (Reset, reduzierte Bewegung). Medienabfragen mit `max-width`: **1** (`filter.css`). Daraus entstanden fünf Regeln (Farben nur in Tokens; `z-index` nur über Token; `!important` nur in den zwei Dateien; keine ID-Selektoren; keine `max-width`-Medienabfragen).
4. Beim ersten Lauf von `npm test` waren **3 von 6 Tests rot**. Zwei davon waren Fehler im Test selbst: Die Farbregel hatte die Tokens-Datei nicht ausgenommen, und der reguläre Ausdruck für `z-index` meldete `z-index: var(--z-badge)` fälschlich, weil er sich zurückverfolgen und das Leerzeichen als „kein Token“ lesen konnte. Der dritte war ein echter Befund: Die Mobile-first-Regel schlug an `filter.css:48 @media (max-width: 26rem)` an. Dort reserviert das CSS Platz für per JavaScript eingefügte Bedienelemente und wurde gegen Layoutsprünge gemessen (Kommentar in der Datei: 81 px bzw. 133 px bei 360 px Breite). Entscheidung: **Ausnahme statt Umbau**, weil die schmale Variante das Ergebnis einer Messung ist. Die Ausnahme steht im Test (`["05-components/filter.css"]`) **und** in `governance.md` mit Begründung. Danach: 6 von 6 grün, `npm test` insgesamt 31 Tests. Merke: Ein roter Test kann am Test liegen. Prüfe neue Tests deshalb an einem bekannten guten **und** einem bekannten schlechten Fall.
5. Auslaufen: (1) Kommentar „veraltet seit …, Ersatz: …“ und Eintrag im CHANGELOG; (2) Übergangszeit von z. B. zwei Releases; (3) Nutzung messen: `npm run namen` meldet CSS-Klassen, die im HTML und JavaScript nicht mehr vorkommen, als Hinweis (derzeit 2: `.mt-0`, `.visually-hidden`), mit Einschränkung: dynamisch zusammengesetzte Klassennamen erkennt er nicht; (4) entfernen, CHANGELOG. Beachte: „ungenutzt“ heißt nicht „überflüssig“ (`.visually-hidden` ist ein Hilfsmittel für künftige Fälle).

   **Nicht getestet:** Wie die Regeln im Team mit mehr als einer Person wirken (Einzelperson-Projekt); Branch-Schutz und CODEOWNERS auf GitHub.
