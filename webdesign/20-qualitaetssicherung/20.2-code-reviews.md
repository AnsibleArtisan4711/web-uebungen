# 20.2 Code Reviews

> Modul 20 · Lehrplan 20.3 · Geschätzter Zeitaufwand: 90 Minuten

## Lernziele

- Du liest eine Änderung wie eine Reviewerin und formulierst konkrete, begründete Rückmeldungen.
- Du erstellst eine Review-Checkliste für Frontend-Änderungen.
- Du trennst, was Maschinen finden, von dem, was nur Menschen sehen.
- Du schreibst eine Pull-Request-Beschreibung, die ein Review erleichtert.

## Voraussetzungen

20.1; Grundkenntnisse in Git (19.1)

## Ausgangslage

Ein Kollege hat einen Pull Request „Hinweisbox“ geschickt. Die Änderung steht in [`docs/review-uebung/aenderung.diff`](../portfolio/modul-20/docs/review-uebung/aenderung.diff) (29 neue Zeilen in drei Dateien). Als Hilfen gibt es die [Review-Checkliste](../portfolio/modul-20/docs/review-checkliste.md) und die [Pull-Request-Vorlage](../portfolio/modul-20/docs/pull-request-vorlage.md).

## Aufgabe

1. Lies den Diff **ohne** Werkzeuge und notiere deine Befunde als „Vorschlag: … weil …“. Markiere jeden Befund als blockierend oder Anregung.
2. Erstelle eine Review-Checkliste für einen CSS-Pull-Request mit mindestens fünf Punkten (Lehrplan-Aufgabe 3). Vergleiche mit [`review-checkliste.md`](../portfolio/modul-20/docs/review-checkliste.md).
3. Wende die Änderung in einer Wegwerf-Kopie an (Git-Repository, Branch, `git apply`) und lasse alle Prüfungen laufen: `npm run lint`, `format:pruefen`, `validate:html`, `validate:w3c`, `security`, `namen`, `css:pruefen`, `npm test`. Welche deiner Befunde hat eine Maschine ebenfalls gefunden? Welche nur du?
4. Schreibe eine Pull-Request-Beschreibung für diese Änderung, die ein Review erleichtert (Vorlage `pull-request-vorlage.md`).
5. Warum sollen Pull Requests klein sein, und warum sollen Stilfragen automatisiert werden?

## Hinweise

- Prüfe auch das Zusammenspiel: Was passiert mit der Änderung unter der strengen Content Security Policy (Modul 18)?
- Formuliere Rückmeldungen als Vorschlag mit Begründung, nicht als Urteil über die Person.
- Notiere, was **nicht** im Diff steht, aber fehlt (Tests, Dokumentation, Screenshots).

## Lösung

1. Befunde aus dem Diff, von Hand (in der Reihenfolge der Dateien):

   **CSS** (`hinweis.css`)
   - *Blockierend:* `#hinweisbox .titel { … !important }`. Vorschlag: Klassen im BEM-Muster statt ID (`hinweisbox__titel`) und `!important` weglassen, weil die Spezifität sonst schwer zu überstimmen ist.
   - *Blockierend:* Keine Tokens. `#C0392B`, `13px`, `7px`. Vorschlag: `var(--color-error)` o. Ä. und Abstandstokens, weil sich Hell/Dunkel-Schema und Abstände sonst nicht mitändern.
   - *Blockierend:* `a:focus { outline: none; }`. Vorschlag: entfernen, weil Tastaturnutzer den Fokus dann nicht sehen (WCAG 2.4.7).
   - *Anregung:* `@media (max-width: 800px)` ist Desktop-first, die übrigen Regeln des Projekts nutzen `min-width`.

   **HTML** (`index.html`)
   - *Blockierend:* `style="margin-bottom:20px"` wird von `style-src 'self'` blockiert und gehört ins CSS.
   - *Blockierend:* `onclick="alert('Hallo')"` wird von der CSP blockiert, und `href="#"` springt nach oben. Vorschlag: ein echter Link oder ein `<button>` mit Ereignis im Skript.
   - *Blockierend:* `<img>` ohne `alt`.
   - *Anregung:* Die Klassen `Hinweis Box` sind groß geschrieben und kommen im CSS nicht vor (`.hinweis` existiert, aber klein geschrieben). Vorschlag: BEM-Name, der zu einer vorhandenen Komponente passt.

   **JavaScript** (`main.js`)
   - *Blockierend:* `box.innerHTML = "Hallo " + name` mit einem Wert aus der Adresse (`?name=…`). Vorschlag: `textContent`, weil sonst jeder Link eine XSS-Lücke sein kann.
   - *Anregung:* `var` statt `const`/`let`, `name` ohne Prüfung auf `null`; die Variable `ungenutzt` löschen.

   **Fehlt:** Beschreibung, Screenshots, Test, Eintrag im Styleguide, Begründung, warum eine Hinweisbox gebraucht wird (die Anforderung kennt nur das Ticket).
2. Mögliche Checkliste (aus dem Lehrplan abgeleitet, vollständige Fassung in [`review-checkliste.md`](../portfolio/modul-20/docs/review-checkliste.md)): (1) Tokens statt fester Zahlen, (2) niedrige Spezifität: keine IDs, kein neues `!important`, (3) Mobile First, (4) Klassennamen im BEM-Muster und nach Bedeutung, (5) Fokus-Stile nicht entfernt, Kontrast geprüft, (6) Gelten die Regeln auch im dunklen Farbschema und mit reduzierter Bewegung? (7) Styleguide und Dokumentation angepasst.
3. Gemessen in einer Wegwerf-Kopie (Branch `feature/hinweisbox`, Änderung wie im Diff):

   | Werkzeug | Ergebnis |
   |---|---|
   | Stylelint | 5 Fehler: `selector-max-id` (2×), `selector-max-specificity` (2×), `declaration-no-important` |
   | ESLint | 2 Fehler (dieselbe Variable): `no-unused-vars`, `prefer-const` |
   | Prettier | 1 Datei nicht formatiert (`hinweis.css`) |
   | html-validate | 2 Fehler: `no-inline-style`, `wcag/h37` (fehlendes `alt`) |
   | W3C-Validator | 1 Fehler (fehlendes `alt`) |
   | `npm run security` | 3 Probleme: Inline-Event-Handler, `style`-Attribut, `innerHTML =` |
   | `npm run namen` | 4 Verstöße: `Box` und `Hinweis` nicht im BEM-Muster, beide ohne CSS-Regel |
   | `npm run css:pruefen` | „css/main.css ist veraltet“ (nicht neu gebaut) |
   | `npm test` | 3 von 13 Tests schlagen fehl: `main.css` aktuell, keine ID-Selektoren, `!important` nur im Reset |

   **Nicht gefunden von irgendeinem Werkzeug:** feste Zahlen statt Tokens (`13px`, `7px`, `#C0392B`), das entfernte Fokusrechteck (`a:focus { outline: none }`), Desktop-first, `href="#"`, `var` statt `const`, die fehlende Beschreibung und fehlende Tests, ob die Hinweisbox überhaupt gebraucht wird. Das sind etwa die Hälfte der Befunde, darunter ein Zugänglichkeitsfehler (Fokus), den nur ein Mensch bemerkt. Außerdem hat ESLint die Variable gemeldet, aber nicht das `var`, weil die Regel `no-var` in der Projektkonfiguration nicht aktiv ist. **Nicht ausgeführt:** Ich habe den XSS-Pfad (`?name=<img …>`) nicht im Browser ausgelöst; der Befund beruht auf dem Muster, das auch `security-check.js` meldet.
4. Beispiel: „**Hinweisbox auf der Startseite** (Ticket #12). Neue Komponente `hinweisbox` mit Titel und Link, Name aus `?name=`. Geprüft: `lint`, `test`, `build`, mobil/Desktop angesehen (Screenshots). Bitte besonders ansehen: Fokus, Umgang mit dem Parameter. Nicht getestet: Firefox/Safari, Bildschirmleser.“ Wichtig sind das Warum, die Prüfung und die ehrliche Liste des Nicht-Geprüften.
5. Kleine Änderungen (Richtwert des Lehrplans: unter etwa 400 Zeilen) lassen sich gründlich lesen, eine große nicht. Stilfragen gehören der Maschine (Prettier, Stylelint), damit Menschen über Inhalt, Zugänglichkeit und Entwurfsentscheidungen sprechen statt über Einrückung. Autorin und Reviewerin haben dasselbe Ziel.

   **Nicht getestet:** Review in einer echten Plattform (GitHub), automatische Zuweisung (`CODEOWNERS`), Branch-Schutz mit Pflicht-Review.

## Erweiterungen

- Schreibe selbst eine Änderung mit drei absichtlichen Mängeln und lass jemanden reviewen (oder lies sie nach einer Woche selbst).
- Lege eine `CODEOWNERS`-Datei an und überlege, welche Dateien eine zweite Person ansehen muss.
