# 16.6 CSS- und JS-Optimierung, HTML-Minimierung und Caching

> Modul 16 · Lehrplan 16.7 · Geschätzter Zeitaufwand: 90 Minuten

## Lernziele

- Du minifizierst CSS und JS und kennst die Größenordnung des Gewinns.
- Du komprimierst mit gzip und Brotli.
- Du wählst die Cache-Strategie für gehashte Dateien und für HTML.

## Voraussetzungen

16.3

## Ausgangslage

Alle Dateien des Portfolios sind lesbar geschrieben, mit Kommentaren. Das bleibt auch im Quelltext so. Für die Auslieferung zählt die Größe.

## Aufgabe

1. Minifiziere `css/main.css`, `js/main.js` und `js/logik.js` mit esbuild (`npx esbuild css/main.css --minify`; die Ausgabe nur messen, den Quelltext nicht überschreiben). Trage die Größen roh, minifiziert, mit gzip und mit Brotli in eine Tabelle ein.
2. Was bringt mehr: Minifizieren oder Komprimieren? Und beides zusammen?
3. Starte `node tools/server.js 8080` und sieh dir die Antwortheader an (`curl -I -H "Accept-Encoding: br" http://localhost:8080/index.html`). Welche Cache-Strategie gilt für `index.html`, welche würde für eine Datei `main.3fa9c1d2.css` gelten, und warum?
4. Was passiert beim zweiten Aufruf von `index.html`, wenn sich nichts geändert hat? Teste mit `If-None-Match`.
5. Wie findest du ungenutzten Code (DevTools *Coverage*), und wann lohnt sich Code Splitting hier nicht?

## Hinweise

- Minifizieren entfernt Leerraum und kürzt Namen. Komprimieren (gzip, Brotli) kodiert wiederkehrende Muster. Beides wirkt, beides zusammen am besten.
- Dateien mit Hash im Namen ändern bei jeder Änderung ihren Namen, sie dürfen deshalb ewig im Cache bleiben.

## Lösung

1. Gemessen (esbuild `--minify`, gzip Stufe 9, Brotli Standard):

   | Datei | roh | roh + gzip | roh + Brotli | minifiziert | min. + gzip | min. + Brotli |
   |---|---|---|---|---|---|---|
   | `css/main.css` | 22.208 B | 6.050 B | 5.315 B | 13.802 B | 3.623 B | 3.200 B |
   | `js/main.js` | 8.142 B | 2.557 B | 2.282 B | 4.691 B | 1.735 B | 1.535 B |
   | `js/logik.js` | 1.458 B | 724 B | 645 B | 562 B | 360 B | 327 B |
   | `index.html` | 4.538 B | 1.598 B | – | – | – | – |
2. Bei CSS spart Minifizieren etwa 38 % (22.208 auf 13.802 B), Komprimieren etwa 76 % (auf 5.315 B mit Brotli). Beides zusammen: 3.200 B, also etwa 86 % weniger. Weil gzip und Brotli Leerraum ohnehin gut verdichten, schrumpft der Unterschied nach der Kompression (5.315 gegen 3.200 B). Die Kompression bringt mehr, aber beides zusammen ist am kleinsten.
3. Gemessen: `index.html` bekommt `Cache-Control: no-cache` und einen `ETag`: Der Browser darf die Datei speichern, muss aber bei jedem Aufruf nachfragen. Eine Kopie `main.3fa9c1d2.css` bekam `Cache-Control: public, max-age=31536000, immutable` (ein Jahr, nie nachfragen). Das ist sicher, weil jede Änderung einen neuen Hash und damit einen neuen Dateinamen ergibt. Bei Brotli kam `Content-Encoding: br`, die CSS-Datei war dann 5.315 B groß.
4. Der Server antwortet auf `If-None-Match` mit dem gespeicherten `ETag` mit `304 Not Modified` und ohne Inhalt (gemessen). Das spart die Übertragung, nicht die Anfrage.
5. DevTools → *Coverage* zeigt, welcher Anteil von CSS und JS beim Laden der Seite ausgeführt wurde. Bei diesem Portfolio sind CSS (13,8 KB minifiziert) und JavaScript (4,7 KB) so klein, dass Code Splitting mehr Anfragen als Ersparnis bringen würde. Das Budget ist in jeder Datei eingehalten.

   **Nicht getestet:** Build-Schritt im Projekt (kommt in Modul 19), CDN, HTTP/2 und HTTP/3 (der Testserver spricht HTTP/1.1), HTML-Minimierung (der HTML-Gewinn ist nach gzip klein, ungeprüft).
