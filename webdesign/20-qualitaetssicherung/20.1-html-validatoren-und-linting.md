# 20.1 HTML-Validatoren und Linting

> Modul 20 · Lehrplan 20.2 · Geschätzter Zeitaufwand: 60 Minuten

## Lernziele

- Du validierst Seiten mit dem W3C-Validator (Nu Html Checker) und mit html-validate und erklärst den Unterschied.
- Du erkennst die häufigsten HTML-Fehler an der Fehlermeldung.
- Du entscheidest, wenn zwei Prüfwerkzeuge sich widersprechen, und hältst die Entscheidung fest.
- Du verankerst Validierung im Editor, im Pre-commit-Hook und in der CI.

## Voraussetzungen

Modul 19; Node.js 22; für den W3C-Validator zusätzlich Java (`java -version`)

## Ausgangslage

Bisher hat nur eine eigene Prüfung ([`security-check.js`](../portfolio/modul-20/tools/security-check.js)) auf HTML geschaut. Jetzt kommen zwei Validatoren dazu: html-validate (reines Node, konfigurierbar, Konfiguration in [`.htmlvalidate.json`](../portfolio/modul-20/.htmlvalidate.json)) und der offizielle W3C Nu Html Checker, der lokal als JAR läuft ([`validate-w3c.js`](../portfolio/modul-20/tools/validate-w3c.js)). Zum Üben liegt die absichtlich fehlerhafte Seite [`docs/validator-uebung/kaputt.html`](../portfolio/modul-20/docs/validator-uebung/kaputt.html) bereit.

## Aufgabe

1. Führe `npm ci` im Ordner `portfolio/modul-20` aus. Prüfe `kaputt.html` mit beiden Werkzeugen: `npx html-validate docs/validator-uebung/kaputt.html` und `node tools/validate-w3c.js docs/validator-uebung/kaputt.html`. Ordne jede Meldung einem Fehlertyp zu und nenne fünf häufige HTML-Fehler (Lehrplan-Aufgabe 1).
2. Baue die Seite (`npm run build`) und prüfe das Ergebnis: `npm run validate:html` und `npm run validate:w3c`. Wie viele Fehler und Warnungen gibt es? Was bedeuten die Hinweise zur „Content Security Policy“, die der W3C-Validator zusätzlich ausgibt?
3. Behebe, was die Werkzeuge im Portfolio finden. Prüfe danach mit **beiden** Werkzeugen erneut. Was passiert, und wie entscheidest du?
4. Beantworte: Wo und wie integrierst du Validierung und Linting in den Entwicklungsprozess (Lehrplan-Aufgabe 2)? Was fängt jede Stufe, was nicht?
5. Der Lehrplan nennt auch den W3C-CSS-Validator. Was würdest du damit prüfen, und warum reicht er allein nicht (Stylelint)?

## Hinweise

- Der W3C-Validator schreibt sein Ergebnis auf den Fehlerkanal (stderr). Das Skript `validate-w3c.js` sammelt und sortiert es für dich.
- html-validate gibt jeder Meldung einen Regelnamen (z. B. `no-dup-id`). Unter `https://html-validate.org/rules/<regel>.html` steht, was sie bedeutet.
- Prüfe Dateien, nicht Webadressen: Der lokale Validator hat bei meinem Versuch mit `http://localhost:…` die Antwort „Forbidden host“ geliefert.

## Lösung

1. Gemessen mit `kaputt.html` (W3C Nu Html Checker 26.11.4, html-validate 11.19.0):

   | Fehler in der Datei | W3C-Validator | html-validate (Regel) |
   |---|---|---|
   | veraltetes Element `<center>` | Fehler: „The center element is obsolete. Use CSS instead.“ | `deprecated`, `element-permitted-content` |
   | `<div>` in `<p>` | Fehler: „No p element in scope but a p end tag seen.“ (der Browser schließt das `<p>` vor dem `<div>` selbst, danach steht `</p>` allein) | `no-implicit-close`, `close-order` |
   | doppelte `id="a"` | Fehler „Duplicate ID a“, zusätzlich Warnung mit der ersten Fundstelle | `no-dup-id` |
   | `<img>` ohne `alt` | Fehler: „An img element must have an alt attribute …“ | `wcag/h37` |
   | ungültiger Attributwert `size="abc"` | Fehler: „Bad value abc for attribute size on element input“ | `attribute-allowed-values` |
   | `lang` am `<html>` fehlt | nur Warnung | Fehler `element-required-attributes` |

   Ergebnis: W3C **5 Fehler und 2 Warnungen**, html-validate **9 Fehler**. Dazu kommt bei html-validate `doctype-style` („DOCTYPE should be uppercase“): Das ist keine Verletzung des Standards (`<!doctype html>` ist gültig), sondern eine Stilregel aus `html-validate:recommended`. Das zeigt den Unterschied: Der W3C-Validator prüft gegen den **Standard**, html-validate zusätzlich gegen **Regeln, die ein Team festlegt**. Fünf häufige Fehler: doppelte `id`, nicht geschlossene oder falsch verschachtelte Elemente (z. B. `div` in `p`), fehlendes `alt`, ungültige Attributwerte, veraltete Elemente (`center`, `font`), fehlendes `lang`. (Nicht geschlossene Tags habe ich in dieser Datei nicht getestet, die anderen schon.)
2. Gemessen auf dem Stand vor meiner Korrektur: **0 Fehler, 3 Warnungen**: „Section lacks heading“ an drei Stellen (zweimal `lebenslauf/index.html`, einmal `styleguide/index.html`). Dazu 45 Hinweise „Resource violates Content Security Policy (meta tag)“ (alle Seiten × CSS/JS). Diese Hinweise sind für **Dateien** ein Messartefakt: Der Validator wertet die `<meta>`-CSP aus, `'self'` trifft auf `file:`-Adressen aber nicht zu, also gilt jede CSS- und JS-Datei als „blockiert“. Im Browser über `http` gibt es 0 CSP-Verstöße (Modul 18, geprüft mit `csp_probe` auf allen 11 Seiten). `validate-w3c.js` zählt diese Hinweise, gibt sie aber nicht aus. Laufzeit: `validate:html` 0,7 s, `validate:w3c` 1,9 s.
3. Die drei Warnungen kamen von Scroll-Wrappern um Tabellen: `<section class="tabelle-wrap" aria-labelledby="t-bem" tabindex="0">`. Ein `section` ohne Überschrift ist nach dem Outline-Modell fragwürdig. Ich habe es zu `<div class="tabelle-wrap" role="region" aria-labelledby="…" tabindex="0">` geändert (gleiche Wirkung für Hilfstechnik: eine benannte Region). Danach meldete **html-validate** drei Fehler `prefer-native-element` („Prefer to use the native section element“). **Die beiden Werkzeuge widersprachen sich.** Beide Seiten sind begründbar: `section` und `div role="region"` sind gültig; der W3C-Hinweis ist nur eine Warnung zur Gliederung, die html-validate-Regel eine Stilregel. Entscheidung: `div role="region"` behalten und die Regel für genau diese Rolle ausnehmen (`"prefer-native-element": ["error", { "exclude": ["region"] }]` in `.htmlvalidate.json`). Nicht per Kommentar im HTML: Eine Kommentardirektive mit `--` löst beim W3C-Validator die Warnung „not mappable to XML 1.0 due to two consecutive hyphens“ aus (so gemessen). Danach: W3C **0 Fehler, 0 Warnungen**, html-validate **0 Probleme**. Die Entscheidung gehört nicht in den Kopf einer Person, sondern in die Konfiguration.
4. - **Editor:** Plug-ins für html-validate und Stylelint geben beim Tippen Rückmeldung (hier nicht getestet).
   - **Pre-commit-Hook:** [`.githooks/pre-commit`](../.githooks/pre-commit) führt jetzt `npm run lint`, `npm run validate:html` und `npm run css:pruefen` aus. Umgehbar mit `--no-verify`.
   - **CI:** [`ci-workflow/ci.yml`](../ci-workflow/ci.yml) enthält `validate:html`, `namen` und `doku`; ein fehlschlagender Schritt blockiert den Merge, wenn der Branch-Schutz das verlangt (siehe 19.1). Den W3C-Validator habe ich **nicht** in die CI aufgenommen, weil er Java braucht; ob die Läufer auf GitHub Java vorinstalliert haben, habe ich nicht geprüft.
   - Fängt jede Stufe alles? Nein: Die Maschine prüft Syntax und Regeln, nicht, ob ein `alt`-Text sinnvoll ist oder die Überschriften eine gute Gliederung ergeben (siehe 20.2).
5. Der CSS-Validator (`jigsaw.w3.org/css-validator`) prüft Syntax und gültige Eigenschaften und Werte. Der Lehrplan weist darauf hin, dass er neue Funktionen teils als Fehler meldet. Stylelint ergänzt Projektregeln (Namen, Spezifität, Duplikate). **Nicht getestet:** Der CSS-Validator ist ein Onlinedienst, den ich hier nicht erreicht habe; die Aussage über neue Funktionen stammt aus dem Lehrplan.

   **Nicht getestet:** HTMLHint, Pa11y und Lighthouse als Prüfer, Editor-Plug-ins, Validierung von Seiten, die erst per JavaScript entstehen, Validierung über eine Webadresse.

## Erweiterungen

- Aktiviere in `.htmlvalidate.json` strengere Regeln (z. B. `heading-level`, `no-redundant-role`) und entscheide über jeden Fund.
- Schreibe eine eigene html-validate-Regel oder -Regeldatei nur für dein Projekt.
