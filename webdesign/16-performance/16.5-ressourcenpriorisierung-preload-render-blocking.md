# 16.5 Ressourcenpriorisierung, preload und Render Blocking

> Modul 16 · Lehrplan 16.6 · Geschätzter Zeitaufwand: 90 Minuten

## Lernziele

- Du setzt `preload`, `preconnect` und `fetchpriority` gezielt ein.
- Du erklärst, wie CSS und JavaScript das Rendern blockieren.
- Du kannst begründen, wann `preload` schadet.

## Voraussetzungen

16.3, 12.1

## Ausgangslage

Der Browser entdeckt manche Dateien erst spät, zum Beispiel eine Schrift, die erst im CSS genannt wird. Mit Hinweisen im HTML sagst du ihm früher Bescheid.

## Aufgabe

1. Öffne [`experimente/preload-ohne.html`](../portfolio/modul-16/experimente/preload-ohne.html) und [`experimente/preload-mit.html`](../portfolio/modul-16/experimente/preload-mit.html) (über den Testserver) und sieh dir im *Netzwerk*-Reiter an, wann die Schrift angefordert wird. Das CSS wird dabei absichtlich 600 ms verzögert.
2. Warum steht in der Preload-Zeile `crossorigin`, obwohl die Schrift von derselben Herkunft kommt? Was passiert, wenn man es weglässt?
3. Wann ist `preload` sinnvoll, wann schädlich? Wann `preconnect`, wann `dns-prefetch`, wann `prefetch`?
4. Wie blockiert CSS das Rendern, wie blockiert synchrones JavaScript, und was macht `defer`? Schlage dazu [12.1](../12-javascript/12.1-einbindung-script-defer-async-module-css.md) nach.
5. Was bewirkt `fetchpriority="high"`, und wo hast du es in diesem Modul eingesetzt?

## Hinweise

- Ein Preload ist ein Versprechen: „Ich brauche das sicher.“ Wird es nicht benutzt, hat es nur Bandbreite gekostet.
- Der Netzwerk-Reiter zeigt die Priorität jeder Anfrage in einer eigenen Spalte (Rechtsklick auf die Spaltenköpfe).

---

## Lösung

1. Gemessen (Startzeit der Schriftanfrage): ohne Preload nach **622 ms**, mit Preload nach **10 ms**. Ohne den Hinweis muss der Browser warten, bis das (verzögerte) CSS geladen und der `@font-face` gelesen ist; erst dann beginnt der Download. Mit `preload` startet er sofort.
2. Schriften werden immer im CORS-Modus geladen. Ein Preload ohne `crossorigin` hat eine andere Anfrageart und wird nicht wiederverwendet. Gemessen: mit `crossorigin` **1** Anfrage für die Schriftdatei, ohne **2** (doppelter Download).
3. `preload`: für Dateien, die sicher gebraucht, aber spät entdeckt werden (Schrift, Hintergrundbild aus dem CSS, LCP-Bild). Viele oder unwichtige Preloads konkurrieren mit wichtigeren Dateien um Bandbreite. `preconnect`: Verbindung zu einem Fremdserver früh aufbauen, nur für wenige kritische Herkünfte. `dns-prefetch`: nur den DNS-Teil, günstiger. `prefetch`: wahrscheinlich nächste Seite, niedrige Priorität.
4. CSS blockiert das Rendern: Der Browser zeigt nichts, bevor das CSS im `<head>` geladen ist (sonst gäbe es kurz ein ungestaltetes Bild). Synchrones JavaScript blockiert zusätzlich das Parsen des HTML, weil es das Dokument ändern könnte. `defer` lädt parallel und führt das Skript nach dem Parsen in Reihenfolge aus. Die Messung der Ladereihenfolge (classic, defer, async) steht in der Lösung zu 12.1. Gegenmaßnahmen: kleines CSS (hier 22 KB roh), Skripte mit `defer`, Drittanbieter spät laden.
5. Es hebt (`high`) oder senkt (`low`) die Priorität einer einzelnen Anfrage. Eingesetzt beim Avatar auf der Startseite und beim ersten Projektbild; beide sind das größte sichtbare Element ihrer Seite (LCP-Element laut Lighthouse).

   **Nicht getestet:** `preconnect`/`dns-prefetch` (es gibt keine Fremdserver im Portfolio), `prefetch`, Critical CSS (Modul 19).
