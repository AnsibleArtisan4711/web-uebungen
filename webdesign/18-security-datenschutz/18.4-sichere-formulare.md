# 18.4 Sichere Formulare

> Modul 18 · Lehrplan 18.5 · Geschätzter Zeitaufwand: 90 Minuten

## Lernziele

- Du prüfst jede Eingabe serverseitig und erklärst, warum Browser-Attribute nicht reichen.
- Du baust Honeypot und Rate-Limit ein und liest ihre Wirkung ab.
- Du erklärst CSRF und warum SameSite-Cookies als Schutz oft genügen.

## Voraussetzungen

18.3; Modul 6 (Formulare)

## Ausgangslage

Das Kontaktformular [`kontakt/index.html`](../portfolio/modul-18/kontakt/index.html) schickt per POST an `/kontakt/danke/`. Der Testserver prüft die Daten ([`tools/server.js`](../portfolio/modul-18/tools/server.js), Funktion `pruefeFormular`). Auf einem statischen Hoster gibt es diese Serverseite nicht; dazu mehr in Modul 19.

## Aufgabe

1. Sieh dir die Formularfelder an. Welche Schutzmaßnahmen stecken schon im HTML (`maxlength`, `required`, `type`, `autocomplete`, `method`)? Was davon schützt wirklich?
2. Sende mit `curl` Anfragen **am Browser vorbei** an den Testserver, in dieser Reihenfolge: (a) eine gültige Anfrage, (b) eine mit gefülltem Honeypot-Feld `website`, (c) eine mit `<script>x</script>` im Namen, (d) eine leere, (e) eine als JSON, (f) eine mit über 10 KB, (g) eine sechste innerhalb einer Minute. Notiere Statuscode und Auffälligkeiten (Header `X-Verarbeitet`, `Retry-After`).
3. Warum antwortet der Server beim Honeypot mit Status 200 und nicht mit einem Fehler?
4. Erkläre CSRF in zwei Sätzen und nenne zwei Gegenmaßnahmen. Braucht das Kontaktformular einen CSRF-Token?
5. Welche Attribute setzt du bei Passwortfeldern? Das Portfolio hat keines; schreibe die Zeile für ein Anmeldeformular und ein Registrierungsformular auf.

## Hinweise

- Beispiel: `curl -i -X POST http://localhost:8080/kontakt/danke/ -d "name=Max&mail=m@example.com&betreff=frage&nachricht=Eine ausreichend lange Nachricht.&datenschutz=ja&website="`
- Zum Neustart des Zählers startest du den Testserver neu. Das Rate-Limit liegt bei 5 Anfragen pro Minute und Adresse und gilt im Speicher des Servers.
- Das Honeypot-Feld liegt mit CSS aus dem Sichtbereich, hat `tabindex="-1"` und `aria-hidden="true"`. Menschen sehen und erreichen es nicht.

---

## Lösung

1. Im HTML stecken `maxlength="80"` (Name), `maxlength="254"` (E-Mail), `required`, `type="email"`, `autocomplete`, `method="post"`, das Honeypot-Feld und eine Checkbox mit `value="ja"` für den Datenschutzhinweis. **Geschützt wird davon nichts:** All das sind Komfort-Funktionen. Wer das Formular umgeht (curl, Entwicklerwerkzeuge), sendet frei, was er will. Deshalb muss der Server jede Eingabe selbst prüfen. `method="post"` ist aber sinnvoll, weil Daten dann nicht in der Adresse stehen (Verlauf, Logs, Referrer).
2. Gemessen gegen den frisch gestarteten Testserver (Chromium nicht beteiligt):

   | Nr | Anfrage | Status | Auffälligkeit |
   |---|---|---|---|
   | a | gültig | 200 | `X-Verarbeitet: ja`, Antwort „Danke, Max Muster!“ (Name wird HTML-maskiert ausgegeben) |
   | b | Honeypot gefüllt | 200 | `X-Verarbeitet: nein`, Antwort ohne Namen |
   | c | Name `<script>x</script>` | 400 | „Prüfe: name“ (der Name darf nur Buchstaben, Leerzeichen, Bindestrich, Apostroph und Punkt enthalten) |
   | d | alle Felder leer bzw. ungültig | 400 | „Prüfe: name, mail, betreff, nachricht, datenschutz“ |
   | e | `Content-Type: application/json` | 415 | |
   | f | Body über 10 KB | 413 | |
   | g | sechste Anfrage innerhalb einer Minute | 429 | `Retry-After: 60` |

   Der Test (c) zeigt, dass die Eingabe schon bei der **Prüfung** abgewiesen wird (Erlaubnisliste). Zusätzlich wird bei der **Ausgabe** maskiert; das ist die zweite Schicht. Eine Nachricht mit `<b>…</b>` im Textfeld wird akzeptiert (200). Der Testserver prüft von ihr nur die Länge und gibt sie nicht aus. Würdest du sie später anzeigen, musst du sie dort maskieren.
3. Ein Bot, der eine Fehlermeldung bekommt, lernt, dass sein Versuch erkannt wurde, und passt sich an. Mit „200 OK“ hält man ihn im Glauben, es sei durchgegangen. Die Anfrage wird aber nicht verarbeitet (`X-Verarbeitet: nein`).
4. **CSRF** (Cross-Site Request Forgery): Eine fremde Seite löst im Browser eines angemeldeten Nutzers eine Anfrage an deine Seite aus, und der Browser schickt dabei die Anmelde-Cookies mit. Gegenmaßnahmen: ein geheimer Token pro Formular/Sitzung, den der Server prüft, und `SameSite=Lax` oder `Strict` bei Cookies. Das Kontaktformular hat **keine** Anmeldung und ändert nichts, was einer bestimmten Person gehört. Ein Token bringt dort wenig; wichtiger sind Rate-Limit und Honeypot. Sobald es Anmeldung gibt, braucht jedes ändernde Formular Schutz. **Nicht umgesetzt:** Das Portfolio hat keinen CSRF-Schutz, weil eine statische Seite keine Sitzung kennt. Das ist eine Begrenzung, kein Beweis, dass es sicher wäre.
5. Anmeldung: `<input type="password" name="passwort" autocomplete="current-password">`. Registrierung und Passwortwechsel: `autocomplete="new-password"`. Das Einfügen aus der Zwischenablage nicht verbieten, damit Passwortmanager funktionieren. Gespeichert wird serverseitig nur ein Hash mit einem modernen Verfahren (Argon2, bcrypt), nie das Passwort selbst.

   **Nicht getestet:** Datei-Uploads (das Portfolio hat keine), Passwortfelder und Passwort-Hashing, CSRF-Token, echte Verteilung auf mehrere Server (das Rate-Limit liegt im Speicher eines einzigen Prozesses), Captchas. Das Rate-Limit zählt nach Adresse; hinter einem Proxy sähe der Server nur die Adresse des Proxys.

## Erweiterungen

- Erlaube im Testserver ein Feld „Telefonnummer“ mit Erlaubnisliste und teste mit curl.
- Lege fest, wie lange du Anfragen speicherst und wo das in der Datenschutzerklärung steht ([`docs/datenschutz-checkliste.md`](../portfolio/modul-18/docs/datenschutz-checkliste.md)).
