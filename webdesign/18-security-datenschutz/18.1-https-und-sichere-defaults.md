# 18.1 HTTPS und sichere Defaults

> Modul 18 · Lehrplan 18.2 · Geschätzter Zeitaufwand: 75 Minuten

## Lernziele

- Du nennst, was HTTPS leistet (Verschlüsselung, Integrität, Authentizität) und was es nicht leistet.
- Du setzt Sicherheits-Header und liest sie in einer echten Antwort ab.
- Du erklärst die Cookie-Flags `HttpOnly`, `Secure` und `SameSite` und misst die Wirkung von `HttpOnly`.

## Voraussetzungen

Modul 17 abgeschlossen; Node.js installiert (`node --version`)

## Ausgangslage

Das Portfolio ist fertig gebaut. Bevor es online geht, prüfst du, welche Schutzmaßnahmen der Server schon mitliefert. Der Testserver [`tools/server.js`](../portfolio/modul-18/tools/server.js) sendet in diesem Modul Sicherheits-Header und kennt zwei Testrouten für Cookies.

## Aufgabe

1. Beschreibe in drei Sätzen, was HTTPS leistet. Nenne eine Gefahr, vor der HTTPS **nicht** schützt.
2. Starte den Testserver mit `npm run serve` im Ordner `portfolio/modul-18`. Rufe in einem zweiten Terminal `curl -I http://localhost:8080/` auf (unter Windows PowerShell: `curl.exe -I http://localhost:8080/`). Welche Sicherheits-Header kommen an? Schreibe für jeden Header einen Satz, was er verhindert.
3. Öffne `http://localhost:8080/cookie-setzen` und danach `http://localhost:8080/cookie-lesen`. Gib in der Konsole der Entwicklerwerkzeuge `document.cookie` ein. Welche Cookies siehst du, welche sieht der Server? Warum ist das so gewollt?
4. Schreibe die Zeile für `Strict-Transport-Security` mit einer Gültigkeit von einem Jahr. Warum kannst du sie mit dem Testserver nicht prüfen?
5. Was geschieht mit einem Bild, das eine HTTPS-Seite über `http://` einbindet (Mixed Content)? Wie findest du solche Stellen im Projekt, ohne HTTPS zu haben? Tipp: [`tools/security-check.js`](../portfolio/modul-18/tools/security-check.js).

## Hinweise

- `curl -I` fragt nur die Kopfzeilen ab. Alternativ: Entwicklerwerkzeuge → Netzwerk → Anfrage anklicken → Antwort-Header.
- Der Server liefert `HttpOnly`-Cookies mit, wenn du im Browser dieselbe Adresse (`localhost`) verwendest.
- Browser ignorieren HSTS, wenn die Seite über unverschlüsseltes HTTP geladen wurde. Der Testserver spricht nur HTTP.

---

## Lösung

1. HTTPS ist HTTP über TLS. Es verschlüsselt die Übertragung (Mitlesende sehen nur Server und Menge der Daten), sichert die Integrität (niemand kann unterwegs unbemerkt etwas ändern) und die Authentizität (der Server ist wirklich der Server zum Zertifikat). Es schützt **nicht** vor Fehlern in der Seite selbst: Eine Seite mit XSS-Lücke bleibt auch über HTTPS verwundbar, und der Betreiber der Seite sieht alle Daten weiterhin im Klartext.
2. Gemessen mit `curl -I http://localhost:8080/` gegen den Testserver:

   | Header | Wert | Wirkung |
   |---|---|---|
   | `X-Content-Type-Options` | `nosniff` | Der Browser darf den Dateityp nicht erraten und führt z. B. eine als Text gelieferte Datei nicht als Skript aus. |
   | `Referrer-Policy` | `strict-origin-when-cross-origin` | Fremde Server erfahren nur die Herkunft, nicht die ganze Adresse (18.6). |
   | `Permissions-Policy` | `camera=(), microphone=(), geolocation=(self)` | Kamera und Mikrofon sind für die Seite und eingebettete Frames gesperrt, Standort nur für die eigene Seite (18.6). |
   | `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'sha256-…'; style-src 'self'; img-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'` | Nur eigene Ressourcen, kein Einbetten der Seite in fremde Frames (18.4). |

   Zusätzlich liefert der Server `Cache-Control: no-cache` und einen `ETag`. Das sind keine Sicherheits-Header, sie stammen aus Modul 16.
3. Gemessen mit Chromium 153: Nach `/cookie-setzen` zeigt `document.cookie` nur `anzeige=hell`. Der Server sieht auf `/cookie-lesen` aber `sitzung=geheim123; anzeige=hell`. Das Cookie `sitzung` hat das Flag `HttpOnly`: Skripte können es nicht lesen, der Browser schickt es trotzdem mit. Wenn ein Angreifer per XSS Skript einschleust (18.2), kann er so die Sitzungskennung nicht abgreifen. Gewollt ist das für alles, was ein Skript nicht braucht (Sitzung, Anmeldung). Das Cookie `anzeige` (z. B. ein Designwunsch) darf für Skripte lesbar sein. `SameSite=Lax` hält beide Cookies bei Anfragen von fremden Seiten zurück (außer bei normalen Link-Klicks), das hilft gegen CSRF (18.4).
4. `Strict-Transport-Security: max-age=31536000; includeSubDomains`. Ein Jahr sind 31 536 000 Sekunden. Der Browser merkt sich dann, die Domain nur noch per HTTPS anzusprechen. Prüfen kannst du es erst mit einem echten HTTPS-Auftritt: Die Header werden im HTTP-Betrieb ignoriert. Vorsicht beim Einschalten: `includeSubDomains` und lange Laufzeiten sind schwer zurückzunehmen, deshalb erst mit kurzem `max-age` (z. B. 300 Sekunden) testen.
5. Browser blockieren aktiven Mixed Content (Skripte, Frames), bei Bildern verhalten sie sich je nach Browser unterschiedlich. Im Projekt findest du solche Stellen, indem du nach `http://` suchst. `node tools/security-check.js` meldet fremde und unverschlüsselte Ressourcen je Seite. Ergebnis für dieses Portfolio: keine.

   **Nicht getestet:** HTTPS selbst (Zertifikat, Umleitung von HTTP auf HTTPS mit Status 301, HSTS), Mixed-Content-Verhalten im Browser, die Header hinter einem echten Hoster. Ob dein Hoster eigene Header erlaubt, klärst du in Modul 19. Wenn nicht, bleibt die `<meta>`-Variante (18.4) mit ihren Grenzen.

## Erweiterungen

- Setze `Secure` im Cookie und überlege, warum der Testserver ohne HTTPS das Cookie dann nicht annimmt.
- Teste deine echte Domain später mit einem Header-Prüfdienst und trage das Ergebnis in [`docs/security-review.md`](../portfolio/modul-18/docs/security-review.md) ein.
