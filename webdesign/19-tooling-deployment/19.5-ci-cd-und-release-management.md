# 19.5 CI/CD und Release-Management

> Modul 19 · Lehrplan 19.6 · Geschätzter Zeitaufwand: 120 Minuten

## Lernziele

- Du erklärst, was eine CI-Pipeline prüft, und liest einen GitHub-Actions-Workflow.
- Du führst die Schritte der Pipeline lokal aus und liest die Zeiten ab.
- Du führst einen Release mit Tag, Changelog und Rollback-Plan durch.
- Du erklärst, warum Hash-Dateinamen die Cache-Invalidierung lösen.

## Voraussetzungen

19.1 bis 19.4

## Ausgangslage

Bisher hast du Prüfungen von Hand gestartet. Eine CI-Pipeline macht das bei jedem Push. Der Workflow liegt in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml), ein Beispiel für die Bereitstellung in [`docs/beispiel-deploy.yml`](../portfolio/modul-19/docs/beispiel-deploy.yml), Checkliste und Rollback-Plan in [`docs/release-checkliste.md`](../portfolio/modul-19/docs/release-checkliste.md).

## Aufgabe

1. Nenne vier Schritte einer CI-Pipeline für ein Webprojekt.
2. Lies `.github/workflows/ci.yml`. Wann läuft der Workflow, mit welchen Rechten, in welchem Ordner? Warum `npm ci` statt `npm install`?
3. Führe die Schritte des Workflows nacheinander in einer frischen Kopie des Projekts aus (ohne `node_modules` und `dist`): `npm ci`, `npm run lint`, `npm run format:pruefen`, `npm run css:pruefen`, `npm test`, `npm run security`, `npm run build`, `npm run links -- dist`, `npm run budget -- dist`. Notiere Ergebnis und Zeit.
4. Prüfe, dass der Workflow gültiges YAML ist (z. B. mit Python `yaml.safe_load`). Was kannst du damit **nicht** prüfen?
5. Führe einen Probe-Release durch: Changelog ergänzen, Tag setzen, bauen. Baue danach vom Tag aus neu. Was zeigt dir der Vergleich der Dateinamen?
6. Beschreibe die Umgebungen Entwicklung, Staging und Produktion und wo dein Projekt steht. Wann würdest du Feature Flags oder Blue-Green-Deployments verwenden?

## Hinweise

- In einer CI-Umgebung ist alles frisch: keine installierten Pakete, keine Zwischenstände. Genau das simuliert die frische Kopie.
- Das Beispiel für die Bereitstellung (`beispiel-deploy.yml`) liegt absichtlich in `docs/` und nicht in `.github/workflows/`, damit es nicht versehentlich läuft.

---

## Lösung

1. Checkout des Codes, Abhängigkeiten installieren (`npm ci`), Lint (Stylelint, ESLint, Format), Tests (Unit- und Build-Tests), Build, danach Bereitstellung auf Staging oder Produktion. Hier zusätzlich: Sicherheitsprüfung, Linkcheck, Größenbudget.
2. Der Workflow läuft bei jedem Push auf `main` und bei jedem Pull Request. Er bekommt nur Leserechte (`permissions: contents: read`, Prinzip der geringsten Rechte), arbeitet im Ordner `portfolio/modul-19` und legt Node-Pakete im Cache ab. `npm ci` installiert **exakt** die Versionen aus `package-lock.json`, bricht ab, wenn `package.json` und Lock-Datei nicht zusammenpassen, und verändert die Lock-Datei nie. `npm install` darf dagegen aktualisieren, und dann ist ein Lauf nicht reproduzierbar.
3. Gemessen in einer frischen Kopie (Node 22.23, npm 10.9, ein Lauf, Pakete aus dem lokalen npm-Cache):

   | Schritt | Ergebnis | Zeit |
   |---|---|---|
   | `npm ci` | 0 Schwachstellen gemeldet | 2,2 s |
   | `npm run lint` | ohne Befund | 1,2 s |
   | `npm run format:pruefen` | alle Dateien formatiert | 0,5 s |
   | `npm run css:pruefen` | `main.css` aktuell | 0,1 s |
   | `npm test` | 13 von 13 Tests bestanden | 2,8 s |
   | `npm run security` | keine Probleme | 0,1 s |
   | `npm run build` | 11 Seiten, `main.5cc722a2.css` | 0,6 s |
   | `npm run links -- dist` | keine Probleme | 0,1 s |
   | `npm run budget -- dist` | Budget eingehalten | 0,1 s |

   Zusammen 7,8 s. Auf GitHub dauert es wegen der Startzeit der Maschine und der Installation länger; die Zahl ist nur eine Untergrenze.
4. Gemessen: `ci.yml` und `beispiel-deploy.yml` sind gültiges YAML (`yaml.safe_load`; Jobs `pruefen` bzw. `bauen`, `veroeffentlichen`). Damit prüfst du nur die **Syntax**. **Nicht geprüft** ist, ob GitHub den Workflow akzeptiert und ausführt, ob die Action-Versionen (`@v4`) aktuell sind (sie stammen aus dem Lehrplan; ich habe sie nicht gegen die aktuellen Veröffentlichungen geprüft), ob `cache-dependency-path` und der Arbeitsordner richtig gesetzt sind. Das erfährst du erst beim ersten Lauf im Reiter „Actions“. Rechne mit einer Korrektur.
5. Probe-Release im Wegwerf-Repository, gemessen: Tag `v1` auf dem Stand mit `main.5cc722a2.css`; danach ein Commit (`--space-1` geändert), Neubau ergibt `main.c8f2e5bf.css`; nach `git switch --detach v1` und Neubau wieder **`main.5cc722a2.css`**. Der Build ist also reproduzierbar: Aus demselben Stand entstehen dieselben Dateien mit denselben Namen (auch der Test `Build ist reproduzierbar` prüft das). Das macht den Rollback verlässlich: Du baust den guten Tag neu, statt auf eine Sicherung von `dist/` zu hoffen. Der Changelog ([`CHANGELOG.md`](../CHANGELOG.md)) hält fest, was in welcher Version geändert wurde; die Versionsnummer folgt Semantic Versioning (Patch, Minor, Major, wie in der Checkliste beschrieben).
6. **Entwicklung**: dein Rechner (`npm run serve`). **Staging**: eine produktionsnahe Kopie zur Abnahme; für das Portfolio z. B. eine Vorschau je Pull Request, falls der Hoster das anbietet (offen, siehe 19.4). **Produktion**: die öffentliche Seite. Für das Portfolio gibt es bisher nur die erste Stufe. Feature Flags (Funktionen im Code ein- und ausschaltbar) und Blue-Green (zwei Produktionsumgebungen, Umschalten per Weiche) lohnen sich bei Diensten mit vielen Nutzern und häufigen Releases, bei einer statischen Seite nicht.

   **Nicht getestet:** Ausführung auf GitHub, Pages-Bereitstellung, Branch-Schutzregeln, Secrets, Blue-Green oder Canary, Rollback auf einem echten Hoster.

## Erweiterungen

- Ergänze den Workflow um einen Job, der den Browser-Pixelvergleich (optional) ausführt.
- Übe den Rollback einmal vollständig nach `docs/release-checkliste.md` und trage das Datum ein.
