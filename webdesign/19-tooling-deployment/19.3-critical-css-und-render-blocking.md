# 19.3 Critical CSS und Render-Blocking

> Modul 19 · Lehrplan 19.4 · Geschätzter Zeitaufwand: 90 Minuten

## Lernziele

- Du erklärst, warum CSS und Skripte das Rendern blockieren, und misst den Unterschied.
- Du setzt Critical CSS ein und lädst den Rest nicht blockierend nach.
- Du erkennst, wo dieses Muster mit einer strengen CSP kollidiert.
- Du entscheidest begründet, ob sich Critical CSS für ein Projekt lohnt.

## Voraussetzungen

19.2; Playwright für Python ist optional (für die Messung)

## Ausgangslage

Das Stylesheet blockiert die erste Darstellung: Der Browser zeichnet erst, wenn es geladen ist. Du baust Testseiten und misst den First Contentful Paint (FCP) bei einem absichtlich langsamen Stylesheet. Die Seiten liegen in [`experimente/`](../portfolio/modul-19/experimente/): `render-a-blockierend.html`, `render-b-critical-inline.html`, `render-c-nur-inline.html`, `script-a-blockierend.html`, `script-b-defer.html`.

## Aufgabe

1. Erkläre, was „Render-Blocking“ bedeutet und welche Ressourcen betroffen sind.
2. Starte den Testserver (`npm run serve`) und öffne `http://localhost:8080/experimente/render-a-blockierend.html`. Das Stylesheet kommt dort 800 ms verzögert (`?delay=800`). Wie lange dauert der FCP? Öffne danach `render-b-critical-inline.html` und `render-c-nur-inline.html`.
3. Öffne `render-b-critical-inline.html` ein zweites Mal mit dem Anhang `?csp=enforce`. Was ändert sich, und warum?
4. Öffne `script-a-blockierend.html` und `script-b-defer.html` (das Skript kommt 800 ms verzögert). Was bewirkt `defer`?
5. Beantworte: Was ist Critical CSS, und wie wird der Rest geladen?
6. Lohnt sich Critical CSS für das Portfolio? Begründe mit Zahlen aus 19.2.

## Hinweise

- Der FCP steht nach dem Laden auf der Seite (`window.ERGEBNIS`) und im Absatz „FCP: … ms“. Es hilft, die Seite ein paarmal neu zu laden und den Median zu nehmen.
- Der Testserver verzögert jede Adresse mit `?delay=800`. Das simuliert eine langsame Verbindung, es ist keine echte Messung für Besucher.
- Das Critical CSS in den Testseiten ist von Hand geschrieben (Schrift, Überschrift, Abstände). Werkzeuge wie das npm-Paket `critical` erzeugen es automatisch.

## Lösung

1. CSS blockiert das Rendern, weil der Browser sonst unstyled Inhalt zeichnen und gleich darauf neu darstellen müsste. `<link rel="stylesheet">` im `<head>` hält also die erste Darstellung auf, bis die Datei da ist. Skripte ohne `async`/`defer` blockieren das Parsen des HTML: Der Browser wartet, lädt und führt sie aus, bevor er weiterliest.
2. Gemessen in Chromium 153, 5 Läufe je Seite, Stylesheet bzw. Skript 800 ms verzögert:

   | Seite | FCP (Median) | `main.css` angewendet |
   |---|---|---|
   | A: normales Stylesheet | **868 ms** | ja |
   | B: Critical CSS inline + Rest per `preload` nachgeladen | **36 ms** | ja (nach dem Nachladen) |
   | C: nur Critical CSS (Kontrolle) | 32 ms | nein |

   Mit Critical CSS erscheint der Inhalt, ohne auf die große Datei zu warten. Die Vergleichsseite C zeigt, dass der Gewinn vom Nicht-Warten kommt: Die nachgeladene Datei wird in B trotzdem angewendet.
3. Gemessen: Unter `?csp=enforce` bleibt der FCP bei 36 ms, aber `main.css` wird **nie** angewendet. Die Seite bleibt dauerhaft ohne das große Stylesheet. Ursache: Die Testrichtlinie erlaubt weder Inline-`<style>` noch Inline-Handler (`onload="…"`), und genau darauf beruht das Muster. Mit der Richtlinie der Portfolio-Seiten (`style-src 'self'`) ginge es also ebenfalls schief. Mögliche Auswege: den Hash des Inline-Styles in `style-src` eintragen und den `onload`-Schritt in eine kleine externe Skriptdatei verlegen. **Das habe ich nicht getestet.** Die Lehre: Prüfe Optimierungen immer zusammen mit der Sicherheitsrichtlinie, nicht getrennt.
4. Gemessen: `script-a-blockierend.html` hat einen FCP von **880 ms**, `script-b-defer.html` von **64 ms**. `defer` lädt das Skript parallel und führt es erst nach dem Parsen aus. Alle Skripte des Portfolios haben `defer`.
5. Critical CSS sind die Styles, die für den sichtbaren Bereich („above the fold“) nötig sind. Sie stehen inline im `<head>`. Das übrige CSS wird nicht blockierend nachgeladen (`rel="preload"` mit `onload`, oder `media`-Trick), mit `<noscript>` als Rückfall.
6. Für das Portfolio eher nicht. Das gesamte Stylesheet hat minimiert 13,9 KB und gzip 3,7 KB (19.2), liegt also unter der Grenze von etwa 20 bis 30 KB, ab der Critical CSS erst interessant wird (Lehrplan). Es kommt aus einer Datei, die nach dem ersten Besuch gecacht ist (`immutable`). Der Preis wären doppelte Pflege (Critical-Teil und Rest), ein Konflikt mit der CSP (Aufgabe 3) und mehr Komplexität im Build. Das gilt für **dieses** Stylesheet; bei einem großen, seitenübergreifenden CSS wäre das Ergebnis ein anderes.

   **Nicht getestet:** das Werkzeug `critical`, echte Netzwerkbedingungen und Geräte (der Testserver simuliert nur Verzögerung), Largest Contentful Paint und Layoutverschiebungen durch nachgeladenes CSS (ohne `size-adjust` o. Ä. kann Inhalt springen), Firefox und Safari.
