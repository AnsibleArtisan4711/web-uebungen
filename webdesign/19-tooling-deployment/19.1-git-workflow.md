# 19.1 Git-Workflow

> Modul 19 · Lehrplan 19.2 · Geschätzter Zeitaufwand: 75 Minuten

## Lernziele

- Du beschreibst den Weg einer Änderung von der Idee bis zum Merge in `main`.
- Du schreibst Commit-Nachrichten nach Conventional Commits und nimmst eine Änderung mit `git revert` zurück.
- Du legst `.gitignore` an und weißt, was nie ins Repository gehört.
- Du aktivierst einen Pre-commit-Hook und liest ab, was er verhindert.

## Voraussetzungen

Modul 18 abgeschlossen; Git installiert (`git --version`)

## Ausgangslage

Das Kursrepository ist gewachsen. Bevor es auf GitHub landet, brauchst du Regeln: Wie entstehen Änderungen, was gehört hinein, was nicht, und wie nimmst du etwas zurück? Die Vorlagen liegen im Repository: [`.gitignore`](../.gitignore), [`.gitattributes`](../.gitattributes), [`.editorconfig`](../.editorconfig), [`.githooks/pre-commit`](../.githooks/pre-commit) und [`docs/git-workflow.md`](../portfolio/modul-19/docs/git-workflow.md).

## Aufgabe

1. Beschreibe in sechs Schritten den Weg einer Änderung von der Idee bis zum Merge in `main`.
2. Lege zum Üben ein Wegwerf-Repository an (Kopie des Kursordners, `git init -b main`). Mache einen Commit auf `main`, dann einen Feature-Branch `feature/impressum-text` mit einem Commit, und führe ihn mit `git merge --no-ff` zurück. Sieh dir `git log --oneline --graph` an.
3. Prüfe, welche Dateien wirklich im Repository landen: `git ls-files | wc -l`. Warum fehlen `node_modules/` und `dist/`? Probiere es aus: Lege `dist/a.txt` an und frage `git check-ignore -v dist/a.txt`.
4. Setze einen Tag `v0.19.0`. Mache danach einen kaputten Commit und nimm ihn mit `git revert` zurück. Wann nimmst du `revert`, wann `reset`?
5. Aktiviere den Hook (`git config core.hooksPath .githooks`, vorher `npm ci` im Ordner `portfolio/modul-19`). Füge in eine CSS-Quelldatei die Zeile `#kaputt { color: red !important; }` ein und versuche zu committen. Was passiert? Wie kommst du im Notfall trotzdem durch, und warum solltest du das nicht zur Gewohnheit machen?
6. Warum steht in `.gitattributes` die Zeile `* text=auto eol=lf`?

## Hinweise

- `git switch` und `git restore` ersetzen die älteren Aufgaben von `git checkout`. Beide sind in Git 2.43 vorhanden (getestet mit dieser Version).
- Lege für den Test eine lokale Identität im Wegwerf-Repository fest (`git config user.name …`, `git config user.email …`), damit nichts an deiner echten Konfiguration hängt.
- Der Hook prüft den ganzen Arbeitsordner, nicht nur die Dateien dieses Commits. Das ist einfacher, aber langsamer als `lint-staged`.

## Lösung

1. Ablauf: (1) `git switch main && git pull`, (2) `git switch -c feature/kurzer-name`, (3) arbeiten und in kleinen, thematischen Commits sichern (`feat:`, `fix:`, `docs:` …), (4) `git push -u origin feature/kurzer-name` und einen Pull Request öffnen, (5) automatische Prüfungen (CI, Übung 19.5) laufen lassen und Review einholen, (6) Merge in `main`, bei einer Veröffentlichung Tag setzen (`git tag -a v0.20.0 -m "…"`). Bei einem Fehler: `git revert`.
2. Gemessen in einem Wegwerf-Repository (Git 2.43.0):

   ```text
   *   <hash> Merge branch 'feature/impressum-text'
   |\
   | * <hash> docs: Hinweis im Impressum ergänzt
   |/
   * <hash> chore: Kursstand bis Modul 19
   ```

   `--no-ff` erzeugt auch dann einen Merge-Commit, wenn `main` unverändert geblieben wäre. So bleibt im Verlauf sichtbar, dass es einen Branch gab. (Die Form des Graphen habe ich im Wegwerf-Repository gesehen; Commit-Texte und Hashes sind bei dir andere.)
3. Im Wegwerf-Repository: 943 Dateien im Repository, davon 0 aus `node_modules`. `git check-ignore -v dist/a.txt` meldet `.gitignore:3:dist/`. Erzeugte und heruntergeladene Dinge gehören nicht hinein: Sie lassen sich neu erzeugen (`npm ci`, `npm run build`), sie machen das Repository groß, und `dist/` würde bei jedem Build Änderungen erzeugen. Ebenfalls draußen: `.env`, `*.pem`, `*.key` (Geheimnisse).

   Beim Testen fiel auf: `node_modules/` (mit Schrägstrich) trifft nur **Ordner**. Wer in einem Test `node_modules` als Symlink anlegt, würde ihn versehentlich committen. In normalen Projekten ist es ein Ordner, deshalb bleibt es bei `node_modules/`.
4. `git tag -a v0.19.0 -m "Stand nach Modul 19"` setzt den Tag. `git revert --no-edit HEAD` erzeugte einen neuen Commit `Revert "feat: kaputt, ohne Hook"`, die Datei war danach wieder im alten Zustand, der Verlauf blieb vollständig. `git switch --detach v0.19.0` führt zum Tag (`git describe --tags` meldet `v0.19.0`), `git switch main` zurück. **`revert`**, wenn der Commit schon geteilt wurde: Er verändert keine Geschichte, die andere schon haben. **`reset --hard`** nur auf eigenen, nicht geteilten Branches, weil es Änderungen verwirft.
5. Gemessen: Der Commit wurde abgebrochen. Ausgabe von Stylelint:

   ```text
   css/src/06-utilities.css
     30:1   ×  Too many ID selectors in "#kaputt", maximum 0       selector-max-id
     30:1   ×  Too high specificity in "#kaputt", maximum "0,3,1"  selector-max-specificity
     30:22  ×  Disallowed !important                               declaration-no-important

   pre-commit: Prüfung fehlgeschlagen. Commit abgebrochen.
   ```

   Mit `git commit --no-verify` geht der Commit trotzdem durch (gemessen). Das ist der Notausgang, etwa wenn du etwas Unfertiges sichern willst. Zur Gewohnheit sollte er nicht werden, denn dann prüft niemand mehr. Darum läuft dieselbe Prüfung zusätzlich in der CI (19.5), die man nicht mit einem Schalter umgeht.
6. Unter Windows speichern Editoren oft CRLF-Zeilenenden, unter Linux und macOS LF. Gemischte Zeilenenden erzeugen sinnlose Diffs und andere Hashes. `eol=lf` hält das Repository einheitlich.

   **Nicht getestet:** Hooks unter Windows (Git for Windows führt sie mit einer eigenen Shell aus; Ausführbarkeit der Datei kann dort abweichen), das Verhalten mit einem echten Remote (`push`, Pull Request, Branch-Schutz), `git rebase`, `lint-staged`.

## Erweiterungen

- Richte in deinem GitHub-Repository „Branch protection“ für `main` ein und verlange grüne CI-Prüfungen.
- Lege einen `.git-blame-ignore-revs`-Eintrag für den Commit an, der den Code formatiert hat (siehe 19.7).
