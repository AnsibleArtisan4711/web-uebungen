# 18.2 XSS-Grundlagen und XSS-Risiken

> Modul 18 · Lehrplan 18.3 · Geschätzter Zeitaufwand: 90 Minuten

## Lernziele

- Du unterscheidest Reflected, Stored und DOM-based XSS.
- Du erklärst, warum `innerHTML` mit Fremddaten gefährlich ist, und ersetzt es durch `textContent`.
- Du misst, dass eine Content Security Policy als zweite Schutzschicht eingeschleusten Code zusätzlich blockiert.

## Voraussetzungen

18.1; `npm run serve` läuft

## Ausgangslage

Das Portfolio schreibt Daten aus der Adresse in die Seite (Suchfeld, Blogfilter). Ein Beispiel dafür, wie das schiefgehen kann, bauen wir in den Experimenten [`xss-unsicher.html`](../portfolio/modul-18/experimente/xss-unsicher.html), [`xss-sicher.html`](../portfolio/modul-18/experimente/xss-sicher.html) und [`xss-unsicher-csp.html`](../portfolio/modul-18/experimente/xss-unsicher-csp.html) nach. Der „Schadcode“ ist harmlos: Er setzt nur ein Attribut am `body`.

## Aufgabe

1. Erkläre den Unterschied zwischen Reflected, Stored und DOM-based XSS in je einem Satz.
2. Öffne `http://localhost:8080/experimente/xss-unsicher.html` und klicke nacheinander auf „Normaler Name“ und „Name mit Schadcode“. Was steht danach im Statusfeld? Sieh dir im Element-Inspektor an, was in `#gruss` steht.
3. Wiederhole den Test mit `xss-sicher.html`. Welche Zeile in [`xss.js`](../portfolio/modul-18/experimente/xss.js) macht den Unterschied?
4. Wiederhole den Test mit `xss-unsicher-csp.html`. Die Seite hat denselben unsicheren Code, aber eine CSP. Was ändert sich im Ergebnis, was nicht?
5. Suche im Projekt nach gefährlichen Schreibzugriffen (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`). Nutze `npm run security` oder deine Editor-Suche. Wo findest du Treffer, und was tust du damit?
6. Beantworte: Warum ist `element.innerHTML = benutzerEingabe` gefährlich, und was ist die sichere Alternative?

## Hinweise

- Die Suche nach `innerHTML` findet auch harmlose Stellen, etwa wenn du den Wert mit einer festen Zeichenkette setzt. Frage immer: Kann hier etwas stehen, das ein Mensch von außen bestimmt hat?
- Es gibt auch Wege über `href="javascript:…"`, `srcdoc` und Vorlagen-Frameworks. Das Prinzip bleibt: Eingaben nie als Code oder Markup behandeln.

## Lösung

1. - **Reflected:** Der Schadcode steckt in der Anfrage (z. B. in der Adresse) und wird sofort in die Antwort übernommen. Der Angreifer braucht einen Link, den das Opfer anklickt.
   - **Stored:** Der Schadcode wird gespeichert (Kommentar, Profil) und trifft jeden, der die Seite ansieht.
   - **DOM-based:** Der Schadcode entsteht erst im Browser, weil ein Skript Daten unsicher ins DOM schreibt. Der Server ist nicht beteiligt.
2. Gemessen in Chromium 153 mit der Adresse `?name=<img src=x onerror="document.body.dataset.xss='ausgefuehrt'">` (URL-kodiert):

   | Seite | Name | Schadcode lief | Inhalt von `#gruss` |
   |---|---|---|---|
   | `xss-unsicher.html` | `Max` | nein | `Hallo Max` |
   | `xss-unsicher.html` | Schadcode | **ja** | `Hallo <img src="x" onerror="document.body.dataset.xss='ausgefuehrt'">` (als Element) |
   | `xss-sicher.html` | `Max` | nein | `Hallo Max` |
   | `xss-sicher.html` | Schadcode | nein | `Hallo &lt;img src=x onerror=…&gt;` (als Text) |
   | `xss-unsicher-csp.html` | Schadcode | nein (Verstoß `script-src-attr`) | wie bei `xss-unsicher.html` |

   Beim unsicheren Code erzeugt `innerHTML` aus dem Text ein `<img>`-Element. Das Bild `x` lässt sich nicht laden, das löst `onerror` aus und führt den eingeschleusten Code aus.
3. In `xss.js` die Zeile `ziel.innerHTML = "Hallo " + name;` gegenüber `ziel.textContent = "Hallo " + name;`. `textContent` setzt nur Text. Das `<` wird zu `&lt;` und bleibt sichtbarer Text.
4. Der Schadcode läuft **nicht** (`window.ERGEBNIS.gelaufen` ist `false`), die CSP meldet einen Verstoß der Direktive `script-src-attr`: Inline-Event-Handler sind ohne `'unsafe-inline'` verboten. Nicht geändert hat sich die Lücke selbst: Das eingeschleuste Element steht weiterhin im DOM (`innerHTML` enthält das `<img>`). Die CSP fängt nur die Folgen ab. Das ist Defense in Depth: Die Lücke schließt man im Code, die CSP ist die zweite Schicht für den Fall, dass man eine übersehen hat.
5. Gemessen: `node tools/security-check.js` meldet für `js/` keine Treffer, `js/main.js` baut alles mit `createElement`, `setAttribute` und `textContent`. Treffer im Experimentordner (`xss-unsicher.html`) sind Absicht und gehören dort hin (das Prüfwerkzeug schaut nur in `js/`). Für einen echten Treffer entscheidest du: (a) durch `textContent` ersetzen, (b) bei nötigem HTML (z. B. Markdown) einen geprüften Sanitizer verwenden, (c) bei festem, selbst geschriebenem HTML belassen und im Code begründen.
6. Die Eingabe wird als HTML gelesen und kann Skript auslösen (XSS). Die sichere Alternative ist `textContent`. Wenn HTML wirklich nötig ist, bereinigt ein Sanitizer die Eingabe vor dem Einfügen.

   **Nicht getestet:** Reflected und Stored XSS (dafür fehlt eine serverseitige Ausgabe von Fremddaten), andere Browser, Sanitizer-Bibliotheken, die Browser-Funktion `setHTML` (Sanitizer API), deren Verfügbarkeit ich nicht geprüft habe.
